50-odd tickets built with an AI workflow, and a low rejection rate.

That's the number I have after seven months with an eight-person development team. It isn't a proper metric yet, and I'll come back to that. But it's what's in front of me day to day, and it's why I stopped measuring these tools on speed.

Here's what the workflow does before anyone opens an editor. Tell it we need to integrate a sensor, give it the API documentation and a blurb on what we know, and it reads the full documentation with our code as context. It builds a multi-card epic: connecting the sensor to the platform, then data ingestion, then data rendering. It writes user stories for every sub-ticket and QA acceptance criteria to go with them. Then it helps the developer turn that scope into a locked-in delivery plan, ticket by ticket.

Not one line of that is code.

Before, the ticket for that same job was "Integrate with Sensor X", a link to the API docs and five or ten lines on what we knew. We don't have a dedicated product manager, so that's how tickets got written. Developers were confused midway through because there were unexpected decisions to make. QA had no clear acceptance criteria. And we were probably skipping the part that would have pushed us to think about what the integration meant for the product as a whole.

The workflow does what good ticket-writing would always have done, except now it's the default rather than something you get when someone has the time.

So when my CEO asked about productivity, I told him I wasn't interested in 10x. Maybe 1.25, maybe 1.5, because we now have autonomous agents dealing with the smaller items. The number I cared about was precision: how well we solve problems for our customers.

The fair pushback is that I've swapped a bad metric for no metric. That one lands. I don't have clear metrics yet, only the 50-odd tickets, the low rejection rate that came with them, and a clear sense from the wider team that we're doing a good job. We're working on embedding those metrics into the workflow now.

Until then, what I see is enough to know the direction is right. The time we've saved on writing code is going back into planning what we write. That was the intent from the start.
